TX Work Order — System Documentation

A Laravel + Vue (Inertia) work order / maintenance management system. It is the operational hub that ties together PropertyWare (system of record), Twilio (SMS), Jobber (field-service scheduling), and an AI-assisted vendor-recommendation workflow.

1 What the System Does

The central entity is the Work Order — a maintenance request tied to a property (Building), an Owner, a Tenant, and one or more Vendors. Work orders originate in PropertyWare and are imported on a schedule. Internal staff called WOCs (Work Order Coordinators) progress each work order through a configurable status workflow, assign vendors, schedule service, exchange SMS with all parties, collect invoices, and close the order back in PropertyWare.

PropertyWare sync

Imports work orders, buildings, owners & vendors; pushes assignments, estimates, schedules, status, approvals, documents & invoices back.

Work-order queues

Organizes open work by service status and specialized queues: inspections, lawn service, turnovers, waiting on payment, paid, closed.

Two-way SMS/MMS

Threaded Twilio conversations between staff and tenants/owners/vendors, matched back to the right work order.

Vendor portal

Passwordless, token-based dashboards: vendors view assignments, submit estimates, upload files/invoices, schedule visits, message coordinators.

Jobber integration

Syncs field-service jobs/visits ("inspections") and texts clients reminders.

AI vendor recommendation

Classifies a work order's issue and recommends a vendor, with deterministic heuristic fallback.

Reporting & onboarding

Calendar, KPI reports, dashboards, task automation, building onboarding incl. onboarding & W-9 PDF generation.

3 Local Setup & Running

This project is configured to run inside Laravel Sail (Docker). Prefix PHP/Artisan/Composer/Node commands with vendor/bin/sail.

# First-time setup
cp .env.example .env
vendor/bin/sail up -d
vendor/bin/sail composer install
vendor/bin/sail artisan key:generate
vendor/bin/sail artisan migrate --seed     # seeds roles & permissions
vendor/bin/sail npm install

# Day-to-day development (server + queue + logs + vite together)
vendor/bin/sail composer run dev

# Or run pieces individually
vendor/bin/sail artisan serve
vendor/bin/sail artisan queue:listen
vendor/bin/sail artisan pail               # live logs
vendor/bin/sail npm run dev                # Vite dev server
vendor/bin/sail artisan reverb:start       # WebSocket server (for realtime)

Build & test

vendor/bin/sail npm run build              # production assets
vendor/bin/sail artisan test --compact     # run test suite
vendor/bin/sail artisan test --filter=Name # single test
vendor/bin/sail bin pint                   # PHP code style (run before committing)
Vite manifest errors ("Unable to locate file in Vite manifest") mean assets aren't built — run npm run dev or npm run build.

5 Data Model

Most models use $guarded = [] (all attributes mass-assignable). Phone numbers on User/Owner/Tenants are normalized to E.164. Several models are filtered per logged-in user via global scopes — see Access Control.

Entity relationship overview

User (roles: admin, woc, accounting, vendor, owner, tenant)
 ├─ hasOne/hasMany → Vendor, Tenants, Owner       (a login may map to a domain party)
 ├─ hasMany       → WorkOrder (as assigned WOC, FK user_id)
 └─ hasMany       → WOCNumbers → TwilioPhoneNumber

Building (one per PropertyWare property)
 └─ hasMany → WorkOrder  (joined on building_id → buildings.propertyware_id)

WorkOrder  (the hub)
 ├─ belongsTo     → User (woc), ServiceStatus, Owner, Tenants, Building
 ├─ belongsToMany → Owner, Tenants, Vendor (work_order_vendors pivot = estimates + access_token)
 ├─ hasMany       → WorkOrderTask, WorkOrderNotes, Conversation, ServiceSchedule, Attachments, Invoice
 └─ hasOne        → Invoice (latest), WorkOrderRecommendation (latestOfMany)

Conversation → hasMany ConversationMedia
ServiceStatus → hasMany WorkOrder            (the workflow stage)
TaskTemplate → hasMany Task → hasMany TaskDetail   (task automation library)

Jobber (jobber_jobs) ── belongsTo → JobberClient, JobberProperty
 ├─ hasMany → JobberVisit, JobberTextMessage, ClientContact
JobberToken (OAuth token storage)

Core domain entities

  • WorkOrder (work_orders) — the hub. Globally scoped by WorkOrderScope (role-based visibility). Conversations split by conversation_type into typed relations. Joins to Building on propertyware_id, not the local PK.
  • Building (buildings) — a PropertyWare property, keyed by unique propertyware_id. Carries maintenance policy fields (notice, spending limits, surcharge, custom fields).
  • Owner / Tenants — property owner / occupant; each belongsTo User and belongsToMany WorkOrder.
  • Vendor (vendors) — contractor, keyed by propertyware_id. Passwordless portal via stable 48-char portal_token.
  • FallbackVendor — backstop vendors for the AI recommendation flow (priority-ranked, keyword/issue-type arrays).

Task / workflow automation

  • ServiceStatus — a stage in the work-order lifecycle (workflow state machine).
  • TaskTemplate → Task → TaskDetail — reusable checklists tied to status transitions, with Yes/No branching.
  • WorkOrderTask — a concrete task instance on a work order. Uses SoftDeletes; scoped by TaskScope.

Communications, documents, scheduling

  • Conversation / ConversationMedia — a single SMS message in a thread + its MMS attachments.
  • Attachments, WorkOrderNotes, WorkOrderDocuments — files & notes on a work order.
  • Invoice — vendor invoice; status (pending/approved/decline), publish flag, scoped by InvoiceScope.
  • ServiceSchedule — a scheduled service appointment / calendar entry; scoped by CalendarScope.
  • WorkOrderRecommendation — AI/heuristic vendor recommendation (one per work order).

Cross-cutting notes

  • Activity logging (Spatie Activitylog) via explicit activity() calls. Table: activity_log.
  • Soft deletes only on WorkOrderTask.
  • Global scopes silently filter WorkOrder, WorkOrderTask, Conversation, ServiceSchedule, Invoice, Attachments per logged-in user/role — key when debugging "missing records."
  • External keys: Building/Vendor/WorkOrder tie to PropertyWare via propertyware_id; Jobber models use jobber_id.

6 Roles, Permissions & Access Control

Authentication is Jetstream + Fortify (email/password, optional 2FA, Sanctum tokens). Roles/permissions use Spatie laravel-permission, seeded in RolesAndPermissionsSeeder.php and AccountingRoleSeeder.php.

RoleScope
adminFull access; bypasses all gates and WorkOrderScope.
wocWork Order Coordinator (core internal staff); view/create/edit, sees all work orders.
accountingFinance/invoices; sees all work orders, lands on the "waiting on payment" page after login.
vendorSees only work orders they are assigned to / have tasks or attachments on.
ownerSees work orders for owners sharing their email.
tenantSees only their own work orders.

Three layers of authorization

  1. Global admin override — AppServiceProvider::boot() registers Gate::before(... hasRole('admin') ...), so admins bypass all gates/policies.
  2. Policies (app/Policies/) invoked via Gate::authorize(...) with custom ability names (e.g. view_vendors, update_user).
  3. Row-level scoping via global Eloquent scopes (app/Models/Scopes/) — WorkOrderScope and siblings restrict which rows each role can query.

Vendor portal (passwordless)

Two custom magic-link middlewares (aliased in bootstrap/app.php) gate the external vendor portal with no login — access is by possession of an unguessable token:

  • vendor.account → ResolveVendorAccountToken: resolves Vendor.portal_token (full dashboard of all the vendor's active work orders). Bad token → 404.
  • vendor.portal → ResolveVendorPortalToken: resolves a single WorkOrderVendor.access_token (one assignment). Bad token → 404.

Building Onboarding (public self-service form)

A public, unauthenticated form that lets a new property owner onboard their building. Share this link directly with owners:

{APP_URL}/onboarding/building

# production: https://txrenters.azurewebsites.net/onboarding/building
# local:      http://localhost:8080/onboarding/building

Route: GET /onboarding/building → BuildingController@create (route name building.create), renders the Building/Create Vue page. No login or token required — the URL itself is the entry point.

  1. Find the building — owner enters property name, full name & contact number; the form calls POST /search-building, which matches the property in PropertyWare on name + owner + phone.
  2. Complete details — maintenance preferences, pet fields, optional W-9 entity/business details, and an on-screen signature.
  3. Submit — calls POST /buildings/{buildingId}/update-custom-fields, writing custom fields, maintenance notice & pet fields back to PropertyWare.
  4. PDF generation — dispatches GenerateOnboardingPdfJob (signed packet) and, if a W-9 name is provided, GenerateW9PdfJob — both on the queue, so a queue worker must be running.
The page is public — only share the link with the intended owner. The submit step writes to PropertyWare, so confirm PropertyWare credentials are configured in the target environment before sending the link.

  • jobs, workOrders — open to any authenticated user (power live list updates).

8 External Integrations

Twilio (SMS / MMS)

  • TwilioService wraps the Twilio SDK. sendMessage() queues outbound SMS (media URLs are appended to the body as text links, not true MMS) and attaches a status-callback URL.
  • InboundTwilioMessageProcessor::process() handles inbound payloads: dedupes by MessageSid, forwards every inbound message to a PlusThis marketing webhook, matches to a work-order thread or a Jobber thread, downloads MMS media, and filters internal mirror echoes.
  • InboundTwilioMessageProcessor::resolveInboundThread() decides which work order a reply belongs to. The outbound “from” number belongs to a coordinator rather than to a work order, so a tenant with two open work orders under the same coordinator has an identical phone pair on both. Tiers, most to least certain: an explicit (Ref: WO#<n>) in the body (matched against work_order_no, then the id for unnumbered work orders, with the thread taken from the phone pair or the work order’s own tenant/owner/vendor); the last message we sent that person about an open work order; the same allowing closed ones; any message on the pair in either direction; then the original exact-string pair match, so nothing that routes today starts being dropped. Numbers are compared on their last ten digits with punctuation stripped. Routing is anchored on outbound messages so one misrouted reply cannot pull later replies onto the same wrong work order, and an ambiguous phone pair logs a warning naming every candidate work order.
  • TwilioPhoneNumberSyncService::sync() upserts the local Twilio number inventory.

PropertyWare (system of record)

Dual transport via PropertyWareService:

  • REST (api.propertyware.com/pw/api/rest/v1) with x-propertyware-* headers — reads + PATCH updates + custom-field PUTs + document/invoice uploads.
  • SOAP ({PROPERTYWARE_URL}?wsdl, TLS 1.2) — vendor assignment, full work-order detail updates, notes, document attach, approval.
Outbound side-effect: when vendor "Texas Home Maintenance Pros" is assigned, changeWorkOrderVendors() POSTs to an internal n8n automation webhook to create a matching Jobber job. (Hardcoded URL — consider redacting for external publication.)

Jobber (field-service scheduling)

OAuth 2.0 with refresh tokens stored in jobber_tokens: /jobber-connect → authorize, /jobber/callback → exchange code & store token. ensureValidToken() refreshes within 5 min of expiry; jobber:refresh-token runs every 30 min. Data via GraphQL (api.getjobber.com/api/graphql). The HMAC-verified webhook dispatches JOB_* / VISIT_* topics to upsert local Jobber records.

AI vendor recommendation (laravel/ai)

WorkOrderRecommendationService classifies a work order's issue and recommends a vendor (owner-preferred → building history → cross-site history → category → fallback). Degrades gracefully: if no AI provider is configured, it falls back to a deterministic keyword/heuristic engine. Provider auto-selects Azure (if AZURE_OPENAI_* set) else OpenAI.

Asana, S3 & Reverb

  • Asana — a single command asana:set-dues sets due dates on subtasks in specific "lease on the market" projects. No webhook/route.
  • S3 — fully configured but the default disk is local; Twilio media → local, Jobber images → public. Set FILESYSTEM_DISK=s3 to switch.
  • Reverb — WebSocket broadcasting; frontend subscribes via Laravel Echo. Set BROADCAST_CONNECTION=reverb and run reverb:start.

10 Frontend Architecture

A single-page app built with Inertia.js v2 + Vue 3. Controllers return Inertia::render('PageName', [...props]); Inertia mounts the matching Vue component from resources/js/Pages/. Bundled with Vite, styled with Tailwind.

  • app.js — bootstraps Inertia, registers Ziggy (route() in JS), pre-registers the UI component library + lucide icons.
  • echo.js — configures Laravel Echo over the Reverb broadcaster (params from VITE_REVERB_*).
  • Layouts — AppLayout.vue (authenticated shell: sidebar nav, header, user menu) and AuthLayout.vue (login/register).
  • Components/ui/ — shadcn-vue-style design system (~50 primitives) on Reka UI / Radix Vue: dialogs, forms (vee-validate + zod), tables, charts (Unovis & Chart.js), sidebar, toast.
  • Pages map 1:1 to controllers; each has a Partials/ folder. The main work-order detail UI is WorkOrder/Partials/WorkOrderDetails.vue (details, tasks, notes, vendor edit, role-based conversation tabs, schedule, invoices, attachments).
  • Forms use vee-validate + @vee-validate/zod with Inertia's useForm; specialized inputs include date pickers, multiselect, image cropper, signature capture.
  • Realtime — pages subscribe via the useEchoPublic composable (e.g. Inspection/Schedules.vue listens for VisitUpdated/VisitDeleted; work-order lists refresh live when the importer ingests new data).

11 Operational Runbook

For the system to function fully in any environment, all three background processes must be running alongside the web server:

1 · Queue worker

queue:work — SMS, PropertyWare write-backs, attachment uploads, PDF generation, AI recommendations.

2 · Scheduler

System cron running php artisan schedule:run every minute drives the import/sync loops.

3 · Reverb server

reverb:start — realtime UI updates.

Common troubleshooting

SymptomLikely cause
"Missing" work orders / records in tinker or for a userA global scope is filtering by role — query as admin or bypass the scope.
Outbound SMS stuck / not sentQueue worker not running, or Twilio creds invalid; check conversations.twilio_status and activity_log.
Inbound SMS not appearingWebhook misconfigured in Twilio console; the 5-min twilio:import-inbound-messages backfill should recover them.
Work orders not importingPropertyWare creds/headers, or the 10-min import:work-orders schedule not running.
Jobber data not syncingOAuth token expired — visit /jobber/diagnose, then /jobber/reconnect.
Frontend change not visible / Vite manifest exceptionAssets not rebuilt — run npm run dev / npm run build.
